# discord-profile-dashboard

## Deployment preparation only

Target approved by owner: Vercel Hobby and Supabase Free. Nothing has been deployed or scheduled by this change. Do not run `npm run backgrounds:cleanup` during preparation: it loads local credentials and mutates database/storage. Normal lint/typecheck/unit/build/browser scripts do not invoke that CLI.

Copy variable names from `.env.example` into the appropriate environment, not real secrets into source control. Blank entries are intentional placeholders, not working configuration. No server secret may use a `NEXT_PUBLIC_` prefix.

- Local development: `APP_URL=http://localhost:3000`, `PROFILE_LEVEL_API_URL=http://127.0.0.1:<LOCAL_BOT_LEVEL_PORT>` (replace the port placeholder). HTTP loopback level access requires `NODE_ENV=development`.
- Production: `APP_URL=https://<PUBLIC_DASHBOARD_HOST>` and `PROFILE_LEVEL_API_URL=https://<PUBLIC_BOT_LEVEL_API_HOST>` must be actual operator-controlled HTTPS origins without paths/query/credentials. Placeholders are not deployment values. Vercel cannot reach the Windows machine through its own localhost or a private LAN address.
- Set `PROFILE_LEVEL_API_ALLOWED_HOSTS=<PUBLIC_BOT_LEVEL_API_HOST>` in production: exact DNS hostnames only, comma-separated if necessary, no scheme/path/port/wildcard. The configured production host must match this operator-maintained allowlist. IP literals, localhost and local/internal reserved suffixes are rejected. This is a configuration allowlist, not DNS-resolution/IP pinning: the operator must ensure the approved host and every DNS answer stay publicly routed and trusted, with no private-address resolution/rebinding. Redirects are rejected and responses have a two-second deadline; users cannot provide the destination.
- Generate an independent random base64url `PROFILE_LEVEL_API_KEY` (32–256 characters, at least 16 distinct characters), shared only by dashboard backend and bot level service. Never reuse `PROFILE_BOT_API_KEY`, the Discord token, or cron/session secrets. `PROFILE_BOT_API_KEY` separately authenticates bot-to-dashboard requests; registry `PROFILE_BOT_GUILD_IDS` must match the intended guilds on both ends.
- Set `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, independent random `SESSION_PASSWORD` (32+ characters), `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` server-side. The service-role key belongs only in the dashboard backend, never in bot or browser. Review hosted migrations, grants/RLS and private bucket policy before production.
- After explicit deployment approval, the operator must generate a separate random base64url `CRON_SECRET` (32–256 characters, at least 16 distinct characters) in a password manager or secure local tool, and set it as a Vercel production secret. Do not paste it in chat, logs or the repository. Vercel sends `Authorization: Bearer <CRON_SECRET>`; cookie sessions and bot keys do not authorize cron. Missing/invalid configuration returns 503; missing/wrong bearer returns 401 before database/storage access.

`vercel.json` prepares one daily GET `/api/cron/background-cleanup` at `0 3 * * *` UTC. Hobby scheduling is daily and can run within the scheduled hour, not at a guaranteed minute. Only a future production deployment activates it. Route responses are private/no-store, contain only counters or fixed error codes, and never contain object keys or lease tokens. Do not expose cron credentials in a browser URL or manual public health check.

Each invocation reuses the existing worker for one batch of **3** stale reservations and at most **3** due cleanup jobs, with no draining loop or immediate retry. Each Supabase fetch has a 2-second timeout; worst-case network budget is 28 seconds (2 initial RPCs plus up to 4 calls per job), below the route's explicit 60-second function budget. Verify the actual Vercel project duration setting before activation. Partial failures/skips return 503 with counters; claim/setup errors return a fixed 503. Vercel cron is not assumed to retry automatically. Existing five-minute leases recover after interruption; failed jobs become due after one minute but may wait until the next daily invocation, and stop being claimed after ten attempts. Concurrent runs retain SQL lease/token protection.

Cleanup only reclaims abandoned processing uploads older than one hour and deletes ledger jobs with no surviving background reference. Ready stored images, level-locked slots, and moderation-disabled images remain retained until owner deletion; cron adds no retention purge. The daily upper bound is 3 claimed jobs, not a promise that the queue clears daily. Monitor backlog/oldest due age and exhausted attempts; sustained arrivals above capacity or failures require an operator-approved capacity/scheduling change, not an unbounded loop.

External bot connectivity is still a blocker: the inspected bot level server intentionally binds only loopback. An operator must choose and secure a public HTTPS gateway/hosting arrangement restricted to the level API, preserve bearer authentication and guild checks, protect the key, and verify Vercel reachability before activation. No tunnel, listener expansion, firewall rule, external service or Windows task is installed here. See `TODO.md` for unresolved production checks.

Checks: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, then `npm run test:e2e`. Unit tests use mocked transports; browser tests use mocked app API responses and a local production server. None establishes hosted security or production connectivity.
